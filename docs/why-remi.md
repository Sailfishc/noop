# 为什么是 Remi：理念和使用场景

[快速上手](quickstart.md)讲「怎么装、怎么用」，这篇讲「为什么这样设计、适合拿来做什么」。给刚加入团队的同事看，读完应该知道：什么事交给 Agent，交出去之后会发生什么，什么时候轮到你出手。

## 一句话

**Remi 让团队里有几个常驻的 AI 同事。** 你在频道里像找同事一样找它，它在一台电脑上用 Codex、Claude Code 或 Pi 把事做完；它卡住了会问人，做完了交给人验收，代码只通过 PR 进仓库，合并永远是人。整套东西部署在公司内网，服务端是一个 Go 程序加一个 SQLite 文件。

## 它想解决什么

每个人自己开一个 Claude Code 或 Codex 已经很好用了。可一到团队里，就会碰到这些事：

- **活是一个人派的，结果却要几个人看。** 你让 Agent 改了接口，测试要同事审，上线要另一个人点。各自的终端里，这些交接全靠人在聊天软件里转述。
- **团队的规矩要一遍遍教。** 「PR 标题用中文」「改订单服务前先跑某个脚本」，每个人的 Agent 各教一遍，新同事的 Agent 又从头来。
- **人一离开，事情就停。** 你合上电脑，跑在你电脑上的 Agent 也就没了；你请假，你派出去的活没人能接。
- **看不清事情卡在谁那里。** Agent 在等你回答，还是你在等它跑完？

Remi 把这些放到一个大家都看得见的地方：频道、线程、任务卡，以及每个人自己的「待你决定」。

## 五条理念

### 1. Agent 是常驻的同事，不是一次性的运行

Agent 有名字、@名、负责人和自己的记忆（`memory.md`），长期待在频道里。找它的方式只有一种：给它发一个事件。人的消息、对它问题的回答、别人交给它的活、定时触发、有人开了 PR，都是事件。它空闲时就开工；正在干活时，做完当前这一步就收到，在同一个会话里接着做。所以你可以**中途插话**，不用等它跑完或者取消重来。

但不是线程里谁说话都会叫醒它。发起人、处理人和 Agent 负责人的回复会送到它那里，其他人在线程里讨论不打扰它，要它听就 @它。

### 2. 任何时候都清楚「球在谁手里」

每件没结束的工作，任何时刻只有一个持球者：某个人，或者 Agent 自己。等你确认开工、等你回答、等你验收、交接给你，球就在你手里，这件事会出现在你的「待你决定」里；否则就是 Agent 在做。任务状态只有 5 个（待办、进行中、待验收、完成、关闭），「需要你」是挂在任务上的标记，不是另一种状态。

人和 Agent 在这件事上是对称的：Agent 用 `remi ask` 问你、用 `remi handoff` 把下一步交给你，你回复或者处理完，球就回到它手里。

球交到你手里的时刻应该只有三个：**对齐**（开工前对一次「做完意味着什么」）、**拍板**（确认开工、选方案、回答它的问题、点交接卡）、**验收**。卡住、失败后等你重试、同一个任务第二次验收，都算「三个时刻之外」。Remi 把每次找人都记下来（找了谁、为了什么），任务详情和「设置 › 协作数据」里能看到这些次数，后面的改动有没有真的省注意力，就看「三个时刻之外」这个数有没有降下来。

### 3. Agent 判断，服务端守边界

「这件事要不要改代码、改哪个仓库、要不要先问人、下一步该谁做」，这些语义上的判断交给 Agent，它用 `remi` 命令把判断说出来；服务端不去猜，只守住少数几条硬边界，并且记下来：

| Agent 说 | 服务端守的边界 |
| --- | --- |
| `remi repo owner/name`：我要改这个仓库 | 机器能访问它；只推 `agent/` 开头的分支，只开 PR |
| `remi ask @某人 问题`：我有个问题，先做别的 | 对方要在这个频道里 |
| `remi handoff @某人 事项`：下一步交给他 | 交给人立即生效；交给 Agent 要有人点一下交接卡，一条链最多 3 个 Agent，不能绕回来 |
| `remi submit 提交了什么`：我向外部服务提交了一次 | 每个任务最多 3 次，失败、超时都算，超过就停下来问发起人 |
| 开工前报对齐：「做完意味着」一到五条 | 每个任务只能对齐一次，第二次服务端拒绝；你点「按这个做」时标准写进任务 |
| 交付时逐条报证据：跑了什么、看了什么、哪条没法验 | 不重跑它的命令；它没提到的标准如实标成「未说明」，不拦交付 |

所以 Remi 里没有「编程任务」和「通用任务」两种类型。产出按实际发生的来：有代码改动就开 PR，有文件就交文件，提交了外部服务就给出引用，什么都没有就是一句回答。

### 4. 默认归团队

- **团队 Agent 是默认形态。** 它跑在管理员接入的常开「团队机器」上，用权限收窄的机器人账号推分支、开 PR，频道里谁都能直接 @，不用等谁确认。它有一个具名的负责人。个人 Agent 也有，默认只给主人自己用。
- **规矩放在它成立的那一层**，只写一次：

  | 层 | 放什么 | 存在哪 | 谁来改 |
  | --- | --- | --- | --- |
  | 团队 | 全队通用的约定（`AGENTS.md`）、skills、MCP 配置 | 团队配置仓库，同步到团队机器 | 走 PR，管理员合并 |
  | 频道 | 这个频道特有的约定、常用仓库 | Remi 服务端 | 频道成员在界面上改 |
  | 个人 | 「我的偏好」：只对自己发起的任务生效，排在频道和团队约定之后 | Remi 服务端 | 本人在设置里改，别人看不到 |
  | Agent | 它自己积累的经验（`memory.md`） | Remi 服务端 | Agent 自己写，负责人可改；只有负责人（团队 Agent 还有管理员）看得到 |
  | 代码仓库 | 怎么构建、测试，新开 worktree 时跑的 `.remi/setup.sh` | 仓库自己 | 随代码走 PR |

- **团队里也有个人空间。** 默认公开不等于什么都公开：私有频道和与单个 Agent 的私聊只有成员看得到，管理员在产品里也看不到；用的还是同一套频道、任务和 Agent，只多一个「谁能看到」。
- **任务可以被接手。** 发起人不在时，频道里的人可以点「接手」，之后由接手的人回答问题、验收，任务卡上记着是从谁手里接的。
- **责任跟着人走。** PR 正文写明是谁通过哪个 Agent 派的；合并、验收和拍板永远由人做。

### 5. 自己部署，机器就是权限边界

服务端在内网一台机器上，机器只往外连服务端，服务端不需要访问任何人的电脑。Agent 能碰什么，由它所在的那台机器决定：同一台机器上的 Agent 共用它的 Runtime、仓库和 Git 凭证，没有按 Agent 单独发的密钥。**共用凭证就是共用权限**：谁 @ 团队 Agent，谁就借用了机器人账号的权限，所以机器人账号只给全队本来都能看的仓库；更敏感的仓库放到另一台机器、另一个账号上。MCP 用到的密钥只留在机器本地，不进仓库，也不进服务端。

规模按 10 人以内、每人 1–2 个 Agent 设计。

## 典型场景

下面每个场景都只用 main 上已有的功能。

### 场景一：改一个接口，中途改主意

> @dev 在 acme/orders 里给下单接口加金额上限校验，超过 10 万返回 400

Agent 认领成任务（`T-0012`），用 `remi repo acme/orders` 声明仓库，机器在 `agent/T-0012` 分支的独立 worktree 里把仓库准备好（有 `.remi/setup.sh` 就先跑一遍）。它改到一半，你在线程里补一句「上限改成按商户配置，默认 10 万」，它做完手上这一步就收到，在同一个会话里接着改。做完后任务变成「待验收」，线程里有总结和 PR 链接；你审过、合并，任务自动变成「完成」。

### 场景二：Agent 拿不准，先问再说

Agent 改到退款逻辑，发现「部分退款要不要也受上限约束」需求里没写。它用 `remi ask @王磊 部分退款也要校验上限吗？` 在线程里问，这个问题同时出现在王磊的「待你决定」里；Agent 不停下来，先做不依赖这个答案的部分。王磊在线程里回一句，答案直接送到它正在跑的会话里。

### 场景三：写完交给另一个 Agent 审，再交给人上线

`@dev` 开完 PR，用 `remi handoff @reviewer 审一下 PR 里的金额校验和测试` 交给审查 Agent。`@reviewer` 是发起人能直接用的 Agent，就马上开工；它要主人确认的话，线程里出一张交接卡，只有它的主人能点。开出的新任务记着「谁 via 谁」。审完它用 `remi handoff @张伟 可以发布了` 把球交给负责发布的人，这件事进了张伟的「待你决定」。一条链最多经过 3 个 Agent，不会互相踢皮球没完。

### 场景四：不用人开口的例行工作

在频道的「成员」面板里给 Agent 设触发器，负责人确认一次之后就自动开工：

- **定时**：「工作日 9:00，汇总昨天合并的 PR 和还开着的 PR，贴在频道里」。
- **有人开 PR**：「acme/orders 有新 PR 时，先读一遍，按团队约定指出明显问题」。
- **有推送**：「main 有推送时，检查一下迁移脚本和文档有没有跟上」。

每次触发都以设置它的那个人的名义开一个任务。定时触发器在上一个任务还在排队或运行时跳过（等 CI、等人拍板的不算）；PR 和推送每次都是新东西，不跳过；每天最多触发 10 次（可以改）；Agent 自己的 `agent/` 分支不会触发，所以 Agent 之间不会互相点火。

要它长期盯着一个项目，没事别出声：几个触发器起同一个职责名（比如「看住主干」），面板上是一组，能一起暂停、看近 7 天怎么样。临时的周期事（比如「每 10 分钟汇报一下 MR」的提醒）也列在同一个面板的「临时」组里，任务卡上也看得到，在哪里看见就在哪里暂停或取消；能开它的人和 Agent 就能停它，所属的任务关掉它也跟着结束。新建的触发器默认只读：只看和说，看完没什么就报「没发现」，频道里什么都不出现。定时触发器还可以带一条检查命令（比如查主干最新一次 CI 的结果），输出和上次一样连引擎都不启动。Agent 发现该做的事不动手，用 `remi propose` 提案；提案攒到你定的时间（默认每个工作日 9:30）合成一张卡片，你写「1 3」就做第 1、3 条，每条变成以你名义的任务，计划就是验收标准。真等不了的标成紧急，立刻给你，每个 Agent 每天最多 2 条，夜里先压着。五件事只占你一次注意力。

### 场景五：不写代码的活

不是每件事都要开 PR：

- **整理材料**：「把这周 #支付后端 里关于对账的讨论整理成一页纪要」。Agent 用 `remi read`、`remi search` 查频道历史，把文档放进工作目录的 `out/`，任务卡上可以预览和下载。
- **处理附件**：你发消息时带的表格或日志会放进它的 `in/`，比如「把附件里的报错按出现次数排个序，找出前三个的原因」。
- **调研对比**：「对比一下这三个限流库，结合我们 orders 的用法给个建议」，产出是一份文档或者一段回答。
- **提交外部服务**：要触发一次部署、渲染或者填一个外部表单时，Agent 每提交一次先 `remi submit` 记一笔。一个任务最多 3 次（失败、超时都算），第 4 次服务端会拒绝，Agent 只能停下来问发起人要不要再试。任务卡上分得清「结果已确认」和「已提交、结果未确认」。

### 场景六：团队的规矩写一次

「PR 标题用中文、正文写测试方法」这类全队约定写进团队配置仓库的 `AGENTS.md`，常用的 skills 和 MCP 也放在那里，改动走 PR，合并后团队机器自动同步。只对某个频道成立的（「#支付后端 的改动都要附对账脚本的输出」）写在频道约定里。Agent 开工时先读频道的，再读团队的；自己学到的经验写进自己的 `memory.md`。新同事、新 Agent 加进来，不用再教一遍。

### 场景七：笔记本合上了，额度也用完了

王磊的 `@acha` 勾了两台电脑：笔记本排第一，公司的台式机排第二，台式机登录的是另一个账号。晚上笔记本上的 Codex 额度用完，正在跑的任务显示「等额度恢复，预计 02:30」，到点在同一个会话里接着干，没有人被叫起来；这期间新派给 `@acha` 的活直接去了台式机。第二天早上笔记本合着，新任务也由台式机接。

要是笔记本是在任务做到一半时合上的，十分钟后王磊会收到一张卡：「笔记本离线 12 分钟了，T-0042 停在上面；检查点 21:40，之后大约 8 分钟的工作要重做」，点「在台式机上继续」，台式机从检查点（推在 `agent/T-0042-wip` 上，连没提交的改动一起）恢复工作目录，读一遍线程，新开会话接着做。他不点，就等笔记本回来在原来的会话里继续。同样，Codex 的额度要到明天早上才恢复、而这台电脑上 Claude Code 还能用时，卡片问的是要不要让这个任务换成 Claude Code 接着做，只换这一个任务。

### 场景八：同事请假，活不断

李华派给 `@dev` 的任务做到一半，Agent 在线程里问了一个问题，李华这周休假。频道里的王磊点「接手」，之后由他回答问题、验收。如果 Agent 是需要主人确认的个人 Agent，接手要等主人点「同意接手」；只接主人派活的 Agent 别人接不了。

### 场景九：自己的事，私下交给 Agent

张伟想让 Agent 帮他整理周末的菜谱，这不关团队的事。他点左侧栏「私聊」里自己的 `@notes`，直接写「把这周的菜谱整理成一张表」，不用 @，`@notes` 就开工，结果回到私聊的线程里。要做的事多了，他建了一个私有频道「私房菜」，把 `@notes` 拉进来，按事情分线程聊。团队里别人在频道列表、搜索、任务页、待你决定里都看不到这些。

在私有频道和私聊里，只有张伟自己的 Agent 会更新记忆，记下的东西也只有张伟在界面上看得到。别人的 Agent 被拉进来干活，不会把这里的事写进它主人能看到的记忆。

### 场景十：稍大的活，先对一次再动手

王磊发「@dev 把对账任务改成按天分批跑」。没写验收标准，又要改好几个文件，`@dev` 先只读不改地看了代码，然后发来一张对齐卡：「做完意味着：1. 对账结果和财务导出一致；2. 跑完不超过 10 分钟；3. 失败的那天能单独重跑。不做：不改导出格式。做法：按天拆成子任务。」王磊把第 2 条改成 5 分钟，点「按这个做」，它在同一个会话里开工，后面不会再问。交付时验收卡写着「3 条标准：2 条已验证，1 条未验证」：前两条它跑了对账脚本和计时，第三条它说明了要在预发环境手动停掉一天再重跑。王磊自己验了第三条，再点验收。

### 场景十一：一个人带三个 Agent

张伟建了三个 Agent：`@orders` 在放订单仓库的电脑上，`@web` 管前端仓库，`@lead` 不碰代码，说明里写着下面这段（可以直接拷贝）：

> 你是领队。收到请求后先想清楚要交付什么，把它拆成互不依赖的几块，用 `remi who` 看谁合适，用 `remi delegate @某个Agent 要做的事` 分出去，每块写成对方能自己检查的结果。全部交回后逐块检查回执：不合格的用 `remi delegate` 打回并说清楚要改什么，合格的汇总成一份交付，说明每块是谁做的、怎么验证的。自己尽量不动手；拿不准的事用 `remi ask` 问对应的 Agent，需要人决定的用 needs_decision 问发起人。

张伟发「@lead 给退款加一个部分退款的入口，后端接口和页面都要」。`@lead` 委派 `@orders` 写接口、`@web` 做页面，然后等着。中途 `@web` 用 `remi ask @orders 部分退款接口的参数是什么？` 问了一句，`@orders` 在自己的电脑上只读地查完回答，没有开新任务。两块都交回后 `@lead` 被叫醒一次，读回执，发现页面没处理接口的 400，用 `remi delegate @web` 打回一次；改好后它交付整体。张伟的待验收里只有 `@lead` 的这一个任务。三个 Agent 都是张伟自己的，全程没有卡片，也不算找他。

## 它不打算做的

- **不是每条消息都叫醒所有 Agent。** 那样噪音大、费用高，Agent 之间还会互相接话停不下来。Agent 只在被 @ 或收到属于它的事件时干活。
- **不做工作流引擎。** 交接加触发器已经能拼出大部分流水线；要更复杂的编排，先说明白现有的拼不出来。
- **不在界面上配 MCP，不做容器和工具链自动安装。** 这些跟着团队配置仓库和机器走。
- **不服务完全不碰 Git 的团队。** 定位是开发团队的工具，包括开发团队的非编程任务。

## 现在走到哪了

说清楚哪些是确定的，哪些还没被实践检验：

- 定位里定的六步（个人空间；对齐、证据和找人次数；机器成池和额度等重置；Agent 之间协作；检查点和两张卡片；长期职责）都已经做完。上面讲到的功能（中途插话、`remi ask`、`remi handoff` 和交接卡、触发器、团队机器和团队配置仓库、频道约定、接手、外部提交计数、对齐、证据、找人次数、额度等重置、个人 Agent 跑在多台电脑上、Agent 之间免卡转交、委派和询问、检查点、换电脑继续和换引擎继续、职责、只读巡视、检查命令、提案和攒批）都已经在 main 上，有自动化测试，但**刚合进来，还没有经过团队一段时间的真实使用**。设计时的约定是每一步先用一周，看「设置 › 协作数据」里的几个数（找人的次数和其中三个时刻之外的占比、人回复「待你决定」要多久、每个任务跑了几轮、有多少任务被取消重来），再决定下一步。
- 什么时候对齐是提示词里的三条文字规则，由 Agent 判断，会有出入；判断偏了就改偏好、频道约定或这三条规则。证据是 Agent 自己报的，服务端不重跑，「已验证」的意思是它说它跑过，命令和输出就在那一条里。
- 外部提交上限由服务端计数，但前提是 Agent 照规矩在提交前运行 `remi submit`；它没有记，服务端也就不知道。
- 「Agent 只能推 `agent/` 分支」由机器的推送流程和平台的受保护分支保证。Claude Code 和 Pi 没有系统级沙箱，所以团队机器上建议用专门的系统用户跑守护进程，机器人账号只给 Developer 权限。
- Pi 不支持 MCP，团队配置里的 MCP 服务器只对 Claude Code 和 Codex 生效。
- 额度用完后等多久，靠的是从 Codex、Claude Code、Pi 的报错文字里读出重置时间。这些文字取自它们的源码和安装包，还没有在真实撞上限时逐个核对过；读不出时间时按间隔重试，只会恢复得晚一点。Remi 不区分订阅和 API，也不记账号，只看「这台电脑上的这个 Runtime 现在能不能干活」。
- 询问另一个 Agent 时它做的是只读运行：Codex 用自己的只读沙箱（`--sandbox read-only`），Claude Code 用 plan 模式并且只给读文件和搜索的工具，Pi 只给 `read,grep,find,ls` 四个工具。这些参数取自它们当前版本的帮助和文档，只有 Claude Code 在本机实际跑过一次。不管哪种，运行结束后它的目录都会被删掉，改过东西会在答案里注明。这不是安全边界，电脑才是边界；它只保证问一句不留下改动。
- 委派和询问的上限（深度 3、直接委派 5、子任务 8、打回 2、询问 3）是按「不超过十个人、每人一两个 Agent」估的，没有实际数据，用起来再按协作数据调。
- 一个任务留在接它的那台电脑上（Runtime 的会话文件在那里）。那台关机后，进行到一半的任务等它回来，或者由 Agent 的主人点卡片换到另一台，从检查点接着做。检查点最多晚 10 分钟，这段时间的工作要重做；会话的上下文带不过去，新会话靠线程和工作目录了解前情。换引擎也一样，新的 Runtime 读不到旧 Runtime 的会话。从不自动换，也不自动换回来。
- 检查点的 `-wip` 提交带 `[skip ci]`，推到 GitLab 时还会带 `ci.skip` 推送选项；GitHub 和 GitLab 都认这两个写法，公司内部基于 GitLab 的平台还没有实际核对过，不认的话会给 `-wip` 分支跑一次 CI，可以在 CI 规则里跳过 `agent/*-wip`。
- 私有频道「管理员也看不到」只在产品里成立：管理服务器的人能直接读数据库文件；Runtime 的会话文件留在干活的那台电脑上，电脑的主人读得到。
- Agent 的记忆界面上只有负责人看得到，但 Agent 不管在哪干活都会读全部记忆，可能在别的频道里说出来。现在的做法是写明「私事别让它记」，等真遇到问题再考虑拆一份私有记忆。
- 只读巡视和询问另一个 Agent 不一样：巡视要能写报告、说话和提案，所以没用 Runtime 自带的只读模式，靠提示词、结束时丢掉对仓库的改动、服务端拒绝 PR、转交和委派来保证。和询问一样，它不是安全边界。
- 检查命令是在 Agent 主人的电脑上跑一条任意的 shell 命令，所以只有主人能确认，改了要重新确认。输出里带了时间戳，每次都算有变化，这只能靠写命令的人注意。
- 提案攒批按服务器的时区算（团队在同一个时区）；各项数字（紧急每天 2 条、一次 5 条、未回答 20 条、「不做」记 30 天、7 天过期）除了紧急的两条，都是估的，用起来再调。Agent 不会自己开工做自己的提案，也没有「自主等级」和空闲时找活干。
- 还没做的：通知到公司 IM（设计好了，先不做，要先确认内网服务器能连上钉钉）、人作为任务的执行者。
