# 为什么是 Remi：理念和使用场景

[快速上手](quickstart.md)讲「怎么装、怎么用」，这篇讲「为什么这样设计、适合拿来做什么」。给刚加入团队的同事看，读完应该知道：什么事交给 Agent，交出去之后会发生什么，什么时候轮到你出手。

## 一句话

**Remi 让团队里有几个常驻的 AI 同事。** 你在频道里像找同事一样找它，它在一台电脑上用 Codex、Claude Code 或 Pi 把事做完；它卡住了会问人，做完了交给人验收，代码只通过 PR 进仓库，合并永远是人。整套东西部署在公司内网，服务端是一个 Go 程序加一个 SQLite 文件。

## 它想解决什么

每个人自己开一个 Claude Code 或 Codex 已经很好用了。可一到团队里，就会碰到这些事：

- **活是一个人派的，结果却要几个人看。** 你让 Agent 改了接口，测试要同事审，上线要另一个人点。各自的终端里，这些交接全靠人在聊天软件里转述。
- **团队的规矩要一遍遍教。** 「PR 标题用中文」「改订单服务前先跑某个脚本」，每个人的 Agent 各教一遍，新同事的 Agent 又从头来。
- **人一离开，事情就停。** 你合上电脑，跑在你电脑上的 Agent 也就没了；你请假，你派出去的活没人能接。
- **看不清事情卡在谁那里。** Agent 在等你回答，还是你在等它跑完？

Remi 把这些放到一个大家都看得见的地方：频道、线程、任务卡，以及每个人自己的「待你决定」。

## 五条理念

### 1. Agent 是常驻的同事，不是一次性的运行

Agent 有名字、@名、负责人和自己的记忆（`memory.md`），长期待在频道里。找它的方式只有一种：给它发一个事件。人的消息、对它问题的回答、别人交给它的活、定时触发、有人开了 PR，都是事件。它空闲时就开工；正在干活时，做完当前这一步就收到，在同一个会话里接着做。所以你可以**中途插话**，不用等它跑完或者取消重来。

但不是线程里谁说话都会叫醒它。发起人、处理人和 Agent 负责人的回复会送到它那里，其他人在线程里讨论不打扰它，要它听就 @它。

### 2. 任何时候都清楚「球在谁手里」

每件没结束的工作，任何时刻只有一个持球者：某个人，或者 Agent 自己。等你确认开工、等你回答、等你验收、交接给你，球就在你手里，这件事会出现在你的「待你决定」里；否则就是 Agent 在做。任务状态只有 5 个（待办、进行中、待验收、完成、关闭），「需要你」是挂在任务上的标记，不是另一种状态。

人和 Agent 在这件事上是对称的：Agent 用 `remi ask` 问你、用 `remi handoff` 把下一步交给你，你回复或者处理完，球就回到它手里。

### 3. Agent 判断，服务端守边界

「这件事要不要改代码、改哪个仓库、要不要先问人、下一步该谁做」，这些语义上的判断交给 Agent，它用 `remi` 命令把判断说出来；服务端不去猜，只守住少数几条硬边界，并且记下来：

| Agent 说 | 服务端守的边界 |
| --- | --- |
| `remi repo owner/name`：我要改这个仓库 | 机器能访问它；只推 `agent/` 开头的分支，只开 PR |
| `remi ask @某人 问题`：我有个问题，先做别的 | 对方要在这个频道里 |
| `remi handoff @某人 事项`：下一步交给他 | 交给人立即生效；交给 Agent 要有人点一下交接卡，一条链最多 3 个 Agent，不能绕回来 |
| `remi submit 提交了什么`：我向外部服务提交了一次 | 每个任务最多 3 次，失败、超时都算，超过就停下来问发起人 |

所以 Remi 里没有「编程任务」和「通用任务」两种类型。产出按实际发生的来：有代码改动就开 PR，有文件就交文件，提交了外部服务就给出引用，什么都没有就是一句回答。

### 4. 默认归团队

- **团队 Agent 是默认形态。** 它跑在管理员接入的常开「团队机器」上，用权限收窄的机器人账号推分支、开 PR，频道里谁都能直接 @，不用等谁确认。它有一个具名的负责人。个人 Agent 也有，默认只给主人自己用。
- **规矩放在它成立的那一层**，只写一次：

  | 层 | 放什么 | 存在哪 | 谁来改 |
  | --- | --- | --- | --- |
  | 团队 | 全队通用的约定（`AGENTS.md`）、skills、MCP 配置 | 团队配置仓库，同步到团队机器 | 走 PR，管理员合并 |
  | 频道 | 这个频道特有的约定、常用仓库 | Remi 服务端 | 频道成员在界面上改 |
  | Agent | 它自己积累的经验（`memory.md`） | Remi 服务端 | Agent 自己写，负责人可改 |
  | 代码仓库 | 怎么构建、测试，新开 worktree 时跑的 `.remi/setup.sh` | 仓库自己 | 随代码走 PR |

- **任务可以被接手。** 发起人不在时，频道里的人可以点「接手」，之后由接手的人回答问题、验收，任务卡上记着是从谁手里接的。
- **责任跟着人走。** PR 正文写明是谁通过哪个 Agent 派的；合并、验收和拍板永远由人做。

### 5. 自己部署，机器就是权限边界

服务端在内网一台机器上，机器只往外连服务端，服务端不需要访问任何人的电脑。Agent 能碰什么，由它所在的那台机器决定：同一台机器上的 Agent 共用它的 Runtime、仓库和 Git 凭证，没有按 Agent 单独发的密钥。**共用凭证就是共用权限**：谁 @ 团队 Agent，谁就借用了机器人账号的权限，所以机器人账号只给全队本来都能看的仓库；更敏感的仓库放到另一台机器、另一个账号上。MCP 用到的密钥只留在机器本地，不进仓库，也不进服务端。

规模按 10 人以内、每人 1–2 个 Agent 设计。

## 典型场景

下面每个场景都只用 main 上已有的功能。

### 场景一：改一个接口，中途改主意

> @dev 在 acme/orders 里给下单接口加金额上限校验，超过 10 万返回 400

Agent 认领成任务（`T-0012`），用 `remi repo acme/orders` 声明仓库，机器在 `agent/T-0012` 分支的独立 worktree 里把仓库准备好（有 `.remi/setup.sh` 就先跑一遍）。它改到一半，你在线程里补一句「上限改成按商户配置，默认 10 万」，它做完手上这一步就收到，在同一个会话里接着改。做完后任务变成「待验收」，线程里有总结和 PR 链接；你审过、合并，任务自动变成「完成」。

### 场景二：Agent 拿不准，先问再说

Agent 改到退款逻辑，发现「部分退款要不要也受上限约束」需求里没写。它用 `remi ask @王磊 部分退款也要校验上限吗？` 在线程里问，这个问题同时出现在王磊的「待你决定」里；Agent 不停下来，先做不依赖这个答案的部分。王磊在线程里回一句，答案直接送到它正在跑的会话里。

### 场景三：写完交给另一个 Agent 审，再交给人上线

`@dev` 开完 PR，用 `remi handoff @reviewer 审一下 PR 里的金额校验和测试` 交给审查 Agent。频道里出现一张交接卡，有人点了同意，`@reviewer` 才开工，开出的新任务记着「谁 via 谁」。审完它用 `remi handoff @张伟 可以发布了` 把球交给负责发布的人，这件事进了张伟的「待你决定」。一条链最多经过 3 个 Agent，不会互相踢皮球没完。

### 场景四：不用人开口的例行工作

在频道的「成员」面板里给 Agent 设触发器，负责人确认一次之后就自动开工：

- **定时**：「工作日 9:00，汇总昨天合并的 PR 和还开着的 PR，贴在频道里」。
- **有人开 PR**：「acme/orders 有新 PR 时，先读一遍，按团队约定指出明显问题」。
- **有推送**：「main 有推送时，检查一下迁移脚本和文档有没有跟上」。

每次触发都以设置它的那个人的名义开一个任务。上一个任务还没结束，这次就跳过；每天最多触发 10 次（可以改）；Agent 自己的 `agent/` 分支不会触发，所以 Agent 之间不会互相点火。

### 场景五：不写代码的活

不是每件事都要开 PR：

- **整理材料**：「把这周 #支付后端 里关于对账的讨论整理成一页纪要」。Agent 用 `remi read`、`remi search` 查频道历史，把文档放进工作目录的 `out/`，任务卡上可以预览和下载。
- **处理附件**：你发消息时带的表格或日志会放进它的 `in/`，比如「把附件里的报错按出现次数排个序，找出前三个的原因」。
- **调研对比**：「对比一下这三个限流库，结合我们 orders 的用法给个建议」，产出是一份文档或者一段回答。
- **提交外部服务**：要触发一次部署、渲染或者填一个外部表单时，Agent 每提交一次先 `remi submit` 记一笔。一个任务最多 3 次（失败、超时都算），第 4 次服务端会拒绝，Agent 只能停下来问发起人要不要再试。任务卡上分得清「结果已确认」和「已提交、结果未确认」。

### 场景六：团队的规矩写一次

「PR 标题用中文、正文写测试方法」这类全队约定写进团队配置仓库的 `AGENTS.md`，常用的 skills 和 MCP 也放在那里，改动走 PR，合并后团队机器自动同步。只对某个频道成立的（「#支付后端 的改动都要附对账脚本的输出」）写在频道约定里。Agent 开工时先读频道的，再读团队的；自己学到的经验写进自己的 `memory.md`。新同事、新 Agent 加进来，不用再教一遍。

### 场景七：同事请假，活不断

李华派给 `@dev` 的任务做到一半，Agent 在线程里问了一个问题，李华这周休假。频道里的王磊点「接手」，之后由他回答问题、验收。如果 Agent 是需要主人确认的个人 Agent，接手要等主人点「同意接手」；只接主人派活的 Agent 别人接不了。

## 它不打算做的

- **不是每条消息都叫醒所有 Agent。** 那样噪音大、费用高，Agent 之间还会互相接话停不下来。Agent 只在被 @ 或收到属于它的事件时干活。
- **不做工作流引擎。** 交接加触发器已经能拼出大部分流水线；要更复杂的编排，先说明白现有的拼不出来。
- **不在界面上配 MCP，不做容器和工具链自动安装。** 这些跟着团队配置仓库和机器走。
- **不服务完全不碰 Git 的团队。** 定位是开发团队的工具，包括开发团队的非编程任务。

## 现在走到哪了

说清楚哪些是确定的，哪些还没被实践检验：

- 上面讲到的功能（中途插话、`remi ask`、`remi handoff` 和交接卡、触发器、团队机器和团队配置仓库、频道约定、接手、外部提交计数）都已经在 main 上，有自动化测试，但**刚合进来，还没有经过团队一段时间的真实使用**。设计时的约定是每一步先用一周，看「设置 › 协作数据」里的几个数（人回复「待你决定」要多久、每个任务跑了几轮、有多少任务被取消重来），再决定下一步。
- 外部提交上限由服务端计数，但前提是 Agent 照规矩在提交前运行 `remi submit`；它没有记，服务端也就不知道。
- 「Agent 只能推 `agent/` 分支」由机器的推送流程和平台的受保护分支保证。Claude Code 和 Pi 没有系统级沙箱，所以团队机器上建议用专门的系统用户跑守护进程，机器人账号只给 Developer 权限。
- Pi 不支持 MCP，团队配置里的 MCP 服务器只对 Claude Code 和 Codex 生效。
- 还没做的：通知到公司 IM、人作为任务的执行者、Agent 的长期职责（比如一直盯着某件事）。
